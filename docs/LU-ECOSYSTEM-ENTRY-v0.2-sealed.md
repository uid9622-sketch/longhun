## 一、设计初心：技术应该服务于人

本项目源于长期的人机协作、知识整理、数学模型探索、系统架构设计和实际工具使用过程。

最初的出发点并不是开发一个新的浏览器，也不是制造一个更复杂的人工智能。

而是一个非常简单的问题：

- 当人工智能、数字工具、网络平台、知识系统和自动化能力越来越多时，普通人为什么还需要分别学习、管理和维护这么多互不兼容的系统？
- 为什么一个人的知识需要分散在不同平台？
- 为什么一个任务需要人工反复解释、复制、粘贴、整理和提醒？
- 为什么不同 AI 不能按照统一规则协作？
- 为什么一个已经产生的知识、公式或经验，换一个工具就可能失去来源、结构和上下文？

因此，本项目希望建立一种新的数字生态组织方式。

让用户只需要提出目标，系统就能够自动理解任务、解析变量、寻找适合的能力、匹配 SOP、组织多个 Agent 并行工作，最终形成可以验证、追溯和持续积累的产品或成果。

**核心理念：**

- 系统是为人服务的，而不是让人满足系统。
- 技术应该降低普通人的使用门槛，而不是制造新的技术壁垒。

## 二、产品核心定位：一个入口，连接整个数字生态

暂定产品名称：**龍魂生态入口（LU Ecosystem Entry）**

未来可形成以下产品体系（父子层级）：

- **龍魂生态入口（总入口）**
  1. **龍魂浏览器**：统一数字生态入口。
  2. **龍魂工作台**：统一任务和智能体协作界面。
  3. **CNSH**：中文原生的机器理解、表达和路由体系。
  4. **LU-123**：动态递归计算与系统状态演化模型。
  5. **LU-AEGO-001**：自主进化与多智能体治理协调器。
  6. **LU-EVOLUTION-MASTER**：知识、算法、人格与能力升级协调系统。

  9. **CNSH FlowField**：多维关系、计算过程和动态协作可视化引擎。

这些不是九个互相独立的软件，它们是一个生态内部不同职责的能力模块。

最终目标是形成：**一个入口、一个主干、多个计算引擎、多个数据源、多个智能体、多个应用场景。**

## 三、第一性原理：LU-123 统一计算主干

LU-123 是整个生态的核心计算思想。它不应只是一个数学计算器，而应该成为不同工具、知识、算法、任务和智能体之间的统一组织逻辑。

核心表达：

```text
x(n+1) = F(x(n), θ(n), c(n))
```

- `x`：当前系统状态、任务、知识或数据。
- `θ`：可调整的参数、权重、策略和配置。
- `c`：当前环境、上下文、外部输入和约束。
- `F`：计算、匹配、路由、协作和状态转移函数。

每次计算形成新的系统状态。完整循环：

```text
1 → N → 1′
```

层级结构（父子集）：

- **1：原始输入与本源**
  - 用户提出一个目标，或者系统发现一个需要处理的事件。
  - 记录原始内容、来源、时间、DNA、上下文和约束。
- **N：多维解析与并行协作**
  - 系统根据任务特征，将其分解为多个独立计算节点，包括：
    - 数学算法解析
    - 知识检索
    - 外部变量解析
    - 数据库检索
    - 向量匹配
    - Agent 能力匹配
    - SOP 自动选择
    - 安全与权限检查
    - 交叉审查
    - 结果验证
  - 各节点可以并行运行，也可以根据依赖关系形成多个计算层级。
- **1′：融合后的新状态**
  - 主控汇总所有有效结果，检查证据和冲突，执行融合计算。
  - 形成新的知识、算法、产品、任务状态或候选升级版本。
  - 新状态保留原始输入与完整演化关系，然后进入下一轮计算。

核心原则：**每次进化都可以产生新状态，但不能抹除原始本源。**

## 四、统一动态计算引擎

未来生态需要一个能够处理不同类型任务的统一计算引擎。

### 4.1 输入解析

输入可以来自：

- 用户自然语言
- 中文 CNSH 指令
- 数学公式
- Python、C、C++ 等程序
- 文档和知识库
- Apple 设备及其数据接口
- Notion 页面和数据库
- Google 服务
- AI 模型
- MCP 和第三方插件
- 本地文件、软件包和代码仓库
- 自动化事件和外部服务

所有输入先进入统一解析层。系统不要求用户提前知道应该使用哪一种工具，由解析引擎识别输入类型、任务目标、变量、约束和所需能力。

### 4.2 变量解析引擎

建立统一变量对象：

```text
Variable = {
  variable_id,
  name,
  source_id,
  source_type,
  data_type,
  value_reference,
  unit,
  timestamp,
  version,
  confidence,
  permission_scope,
  provenance,
  status
}
```

变量分类（父子层级）：

- **变量（Variable）**
  1. **内部变量**：LU-123、五行参数、任务状态、Agent 能力等。
  2. **外部变量**：Apple、Google、Notion、互联网服务等提供的数据。
  3. **环境变量**：操作系统、设备能力、网络状态、资源限制。
  4. **用户变量**：明确授权的偏好、任务目标和配置。
  5. **派生变量**：由公式、模型和其他变量计算得到。
  6. **未知变量**：缺少来源、无法确认或尚未解析的数据。

约束：

- 未知变量不能自动伪装成真实数据。
- 外部变量必须携带来源、时间、权限和版本信息。

### 4.3 统一计算公式

建立生态任务匹配函数：

```text
M(task, agent, sop, context)
```

- `task`：当前任务特征。
- `agent`：可调用的能力。
- `sop`：可用执行流程。
- `context`：环境、约束、权限和上下文。

候选匹配：

```text
Score(i) =
    w1 × CapabilityMatch(i)
  + w2 × ContextMatch(i)
  + w3 × EvidenceMatch(i)
  + w4 × Compatibility(i)
  + w5 × ResourceFit(i)
```

- 其中所有权重必须经过定义、校准和版本管理。
- 安全性、授权和硬性约束不允许被普通匹配分数抵消。

最终选择：

```text
BestRoute = argmax Score(i)
前提：Eligible(i) = TRUE
```

没有符合条件的能力时，返回 `UNKNOWN` 或 `WAIT`，不得强行匹配。

### 4.4 动态 SOP

SOP 不再只是静态文档，它是可以被计算、匹配、组合和调用的执行流程对象。

一个 SOP 包含：

```text
SOP_ID
SOP_VERSION
INPUT_SCHEMA
REQUIRED_VARIABLES
CAPABILITY_REQUIREMENTS
PRECONDITIONS
EXECUTION_GRAPH
PARALLEL_GROUPS
DEPENDENCIES
OUTPUT_SCHEMA
VALIDATION_RULES
ROLLBACK_RULES
PERMISSION_REQUIREMENTS
PROVENANCE
DNA
```

当用户提出一个任务：

```text
输入 → 解析 → 变量提取 → SOP 检索 → 能力匹配 → 动态组装 → 执行 → 验证 → 归档
```

- 系统根据任务选择最高匹配的合法 SOP。
- 多个 SOP 可以组合成新的候选执行流。
- 但原 SOP 不被覆盖，新组合产生独立版本。

**一句话，一个产品可以成为一个动态 SOP 的输出。**

## 五、多智能体并行协作：LU-AEGO-001

完整名称：**Autonomous Evolution & Governance Orchestrator** —— 生态的自主进化与人格协同治理核心。

### 5.1 1→N→1′ 并行拓扑

任务进入主控后，不是简单地依次交给不同 Agent，而是形成动态计算网络。例如：

```text
TASK_INPUT
├── Agent A：数学算法分解
├── Agent B：安全审计
├── Agent C：合规校验
├── Agent D：知识检索
├── Agent E：架构分析
├── Agent F：代码实现
├── Agent G：交叉审查
├── Agent H：实验验证
└── MASTER：结果汇总与融合
```

每个 Agent 都有独立身份、能力向量、权限边界和执行记录。

### 5.2 人格能力向量

```text
A_i(t) = [
  algorithm,
  knowledge,
  security,
  architecture,
  implementation,
  verification,
  reasoning,
  resource_efficiency
]
```

代表某个 Agent 在特定版本下的能力描述。

- 能力值必须来自可验证的任务记录和测试结果。
- 不能仅凭 Agent 自己宣称能力提高。

### 5.3 人格联动矩阵

```text
W(t) = [w_ij(t)]
```

`w_ij` 表示 Agent i 与 Agent j 在特定任务类型下的协作关系参数，用于计算：

- 能力互补程度
- 历史协作表现
- 交叉验证价值
- 任务依赖关系
- 冲突概率
- 协作资源消耗

注意：

- W 不代表人格之间的绝对等级。
- 不同任务可以形成不同的协作矩阵。

### 5.4 并行融合公式

设 N 个 Agent 返回结果 `R = {r1, r2, ..., rN}`，每个结果包含：

```text
Result_ID
Agent_ID
Task_ID
Input_Hash
Output
Evidence_ID
Confidence
Execution_Status
Resource_Cost
Version
```

融合函数：

```text
R_final = Fuse(R, W, E, P)
```

- `W`：协作矩阵。
- `E`：证据集合。
- `P`：权限及安全策略。

融合时必须执行：

1. 检查所有必需节点是否返回。
2. 检查结果是否对应同一个任务版本。
3. 检查证据是否存在。
4. 检查不同 Agent 的结论冲突。
5. 检查是否出现未经授权的操作。
6. 检查输出是否满足任务验收条件。

约束：

- 超时、失败和缺失结果必须明确标记。
- 不能把缺失回执当成通过。

### 5.5 自主进化循环

```text
DISCOVER → COLLECT → REGISTER → ANALYZE → CALCULATE
→ PROPOSE → PEER_REVIEW → P05_AUDIT → TEST → VERSION → ARCHIVE
```

- P05 独立审计。
- 数学引擎验证公式。
- 架构引擎验证依赖。
- 实验引擎验证实际效果。
- 安全引擎验证权限。
- **UID9622 保留最终治理权。**
- 任何 Agent 不得独立批准自身升级。

## 六、五行计算与三色审计：统一调度逻辑

五行不是替代计算机科学中的类型系统、权限系统和数学算法，而是本生态用于组织任务分类、关系表达、状态可视化和调度策略的原创计算抽象。

五行映射（父子层级）：

- **五行**
  - **金**：规则、边界、签名、权限、审计。
  - **水**：知识、记忆、DNA、索引、追溯。
  - **木**：生长、扩展、开发、安装、能力升级。
  - **火**：执行、通信、事件、联网、传播。
  - **土**：存储、归档、容器、数据库、基础设施。

相生相克矩阵：

```text
G[a][b] = 1，当 a 生 b      （相生矩阵 G）
K[a][b] = 1，当 a 克 b      （相克矩阵 K）
```

- 用于建立任务之间的依赖、促进和约束关系。
- 但实际执行权限必须由独立安全策略控制。

数字根：

```text
dr(n) = 1 + ((n - 1) mod 9)，n > 0
dr(0) = 0
dr(dr(n)) = dr(n)      ← 数学上的压缩不动点性质
```

数字根可以作为辅助分类和可视化变量。

**重要区别：** 数字根、五行映射不能单独证明软件安全、身份真实或任务正确。它们是调度和表达层的计算特征，真实安全判断仍然需要签名、证据、权限和测试。

三色审计采用严格合并规则：

- **存在任意红色 → 整体红色。**
- **没有红色，但存在黄色 → 整体黄色。**
- **全部绿色 → 整体绿色。**
- **任何未知状态不得自动视为绿色。**

## 七、统一数据底座：数据库、索引、向量与知识本源

生态需要一个统一的数据组织体系，但不要求所有数据进入同一个数据库，采用多引擎协作。

### 7.1 数据引擎

- **SQLite**：本地元数据、任务状态、变量注册表、关系索引和审计账本。
- **文件仓库**：原始文件、代码、文档、加密包和版本快照。
- **全文检索**：关键词、标题、内容、协议 ID 和 DNA 检索。
- **向量数据库**：语义相似度、知识关联、SOP 匹配和 Agent 能力检索。
- **关系图引擎**：知识节点、工具节点、任务节点、来源节点及其关系。
- **对象存储**：大文件、密文包和可迁移数据对象。

未来可以根据规模接入 PostgreSQL、向量数据库及分布式存储。

### 7.2 统一对象身份

所有知识、任务、公式、SOP、Agent、软件和工具都拥有独立 ID。统一对象结构：

```text
OBJECT = {
  object_id,
  object_type,
  original_id,
  parent_id,
  dna,
  source_id,
  version,
  content_reference,
  metadata_reference,
  vector_reference,
  relation_reference,
  audit_reference,
  timestamp,
  status
}
```

- 每个对象可以拥有多个索引，但只能有一个明确的原始身份。
- 不同数据库之间通过 `object_id` 和关系映射联动。
- 不允许因为数据迁移而丢失原始来源。

### 7.3 向量与原始数据分离

向量只用于检索和匹配；向量不是原始知识，也不是原始公式。正确关系：

```text
原始内容 → 结构解析 → Embedding → 向量索引 → 检索召回 → 原始内容复核
```

Embedding 模型升级时：

1. 保留原始内容。
2. 记录模型名称和版本。
3. 保留旧向量版本。
4. 生成新向量索引。
5. 验证召回效果后再切换。

不能因为向量模型升级而覆盖知识本源。

### 7.4 分布式协作

各个平台、设备和数据库可以作为独立节点，节点之间通过统一协议交换必要信息。同步对象：

```text
OBJECT_ID
SOURCE_ID
VERSION
CONTENT_HASH
RELATION_DELTA
TIMESTAMP
PERMISSION_SCOPE
SYNC_STATUS
```

冲突处理：

- 原始版本保留。
- 新修改形成派生版本。
- 冲突单独登记。
- 按权限和策略决定合并。
- 不能静默覆盖。

支持离线工作、延迟同步、增量同步和失败恢复。

## 九、统一接口与路由：让工具能够互相理解

建立 **CNSH Interface Gateway**，每个外部工具通过独立适配器接入。

统一接口结构：

```text
REQUEST = {
  request_id,
  task_id,
  source_id,
  target_id,
  operation,
  input_schema,
  variable_refs,
  context_refs,
  permission_scope,
  timeout_policy,
  audit_policy
}

RESPONSE = {
  request_id,
  task_id,
  provider_id,
  output_reference,
  evidence_reference,
  status,
  error_code,
  timestamp,
  version
}
```

路由引擎负责：

1. 识别任务。
2. 识别目标工具。
3. 检查接口兼容性。
4. 检查授权。
5. 计算最佳路由。
6. 调用适配器。
7. 接收结果。
8. 验证返回值。
9. 写入任务账本。

- 接口失败时，不得自动绕过权限或切换到未经批准的服务。
- MCP 可以作为外部工具连接标准之一，但不替代生态内部的身份、权限和审计协议。

## 十、CNSH FlowField：双视觉流场与三维生态

CALLS

## 十一、软件 DNA 与本地优先安全体系

本地优先是生态的基础原则。核心口径：

- **云端不是大脑。**
- **云端是经过授权的数据存储、同步和索引节点。**
- **本地负责真正的安全判断和执行。**

软件处理流程：

```text
任意软件下载 → 本地隔离 → 文件身份识别 → SHA256 → 数字签名验证
→ SBOM → 权限和依赖扫描 → 风险分析 → Software DNA
→ 本地加密 → 授权同步 → 云端密文归档
```

软件 DNA 结构：

```text
SoftwareDNA = HASH(
    FileHash
  + Signature
  + SBOMHash
  + PermissionVector
  + SourceID
  + Version
)
```

- 完整报告与密钥保留本地。
- 密文回云前进行脱敏、密文完整性和接收端验证。

云端不得默认接触：

- 原始软件
- 私钥
- Token
- `.env`
- 完整本地日志
- 未授权个人信息

加密算法采用经过审查的标准实现，密钥由本地密钥管理模块保护。

## 十二、DNA 本源与完整演化链

本源是整个生态不能丢失的核心。任何一个知识、算法、任务、产品或 Agent 的升级，都必须保留来源。

建立统一追溯链：

```text
ORIGIN → DESIGN → VARIABLE → FORMULA → CODE
→ EXECUTION → EVIDENCE → AUDIT → DECISION → RELEASE
```

每个环节记录：

- 原始来源
- 对象 ID
- DNA
- 版本
- 时间
- 参数
- 修改内容
- 操作主体
- 测试结果
- 审计结果
- 父子关系

规则：

- 任何修改都产生新的演化记录。
- 原始版本保持只读。
- DNA 用于身份和完整性关联，但不能单独证明内容真实或作者身份。
- 正式签章采用独立的数字签名机制。

**系统允许无限派生，但不允许无来源派生。**

## 十三、开放生态：一句话，一个产品

这是整个项目最重要的长期产品理念之一。

传统软件开发通常要求用户先学习编程语言、开发框架、数据库、接口和部署流程。本项目希望探索另一种方式：

```text
用户提出想法 → 系统解析需求 → 自动提取变量 → 自动匹配知识和算法
→ 自动匹配 SOP → 自动选择 Agent → 自动组织并行任务
→ 自动形成产品结构 → 自动生成候选实现 → 自动测试、审计和归档
→ 用户决定是否正式发布
```

例如，用户提出：「我想建立一个能够自动审计开源软件的工具。」

生态自动匹配：

- 软件 DNA 引擎
- 开源许可证审计
- SBOM 引擎
- 安全扫描
- 本地加密
- CNSH 流场展示
- 多 Agent 交叉审查
- 产品构建 SOP

最终形成一个独立产品候选。

这里的重点不是让 AI 随意创造软件，而是让一个人的想法能够自动进入可计算、可组织、可验证的工程流程。

**一个想法可以成为一个任务，一个任务可以成为一个 SOP，一个 SOP 可以组合多个引擎，一个经过验证的 SOP 可以成为一个产品。**

## 十五、技术落地路线

  - Agent 能力描述
  - 路由协议
  - 三色审计规则
- **验收**：同一任务可以在不同模块之间保持身份和来源一致。

- **目标**：实现 `1→N→1′`。

## 十六、长期愿景：建立一个可以持续成长的数字生态

未来的数字世界不应该只有大型平台和封闭工具。

普通人也应该能够拥有自己的知识体系、计算能力、智能体、产品和数字工作空间。

- 一个人不一定需要成为程序员，才能提出有价值的技术想法。
- 一个人也不应该因为不懂英语、不懂代码、不熟悉复杂的软件工程，就失去创造产品的机会。

本项目希望通过统一计算主干、动态 SOP、开放接口和多智能体并行协作，降低创造和协作的门槛：

- 让不同语言、不同平台、不同模型、不同数据库能够共同参与。
- 让知识持续积累。
- 让算法持续演化。
- 让每个产品保留来源。
- 让每个节点知道自己从哪里来、与谁关联、执行了什么、产生了什么结果。

最终形成：

> **一个入口，连接万物。**
>
> **一个主干，调度万物。**
>
> **一个本源，贯穿万物。**
>
> **一个想法，能够成为一个经过验证的产品。**
