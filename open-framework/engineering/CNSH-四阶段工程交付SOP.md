# CNSH 四阶段工程交付 SOP

## Micro Loop → Integration → Acceptance → Delivery

版本：v1.0\
状态：DRAFT\
适用范围：原始内容留存、结构化暂存、本地存储、索引与关系库、2D/3D/动态渲染、渲染路由、跨平台转换、Notion 同步、复制粘贴与格式清洗，以及后续新增的工程模块。

---

# 0. 总体执行原则

## 0.1 四阶段总流程

```
原始需求与样本
      │
      ▼
P1：最小闭环 Micro Loop
      │
      ▼
真实运行结果
      │
      ▼
P2：结构与底座串联 Integration
      │
      ▼
统一字段、数据结构、存储与路由
      │
      ▼
P3：验收与复核 Acceptance
      │
      ▼
质量检查、边界测试、缺陷定级
      │
      ▼
P4：正式交付 Delivery
      │
      ▼
版本冻结、交付清单、追溯归档
```

任何阶段失败，都必须记录失败原因、证据和回退位置。

禁止：

- 将设计方案写成已实现。
- 将代码生成写成已运行。
- 将单元测试通过写成全系统验收通过。
- 将哈希值写成作者身份或真实性证明。
- 将 Notion 页面存在写成底层本地功能已经部署。
- 未经授权修改原始文件、生产数据库或既有正式版本。
- 发生错误后静默覆盖原内容或删除失败记录。

## 0.2 统一状态定义

| 状态                   | 触发条件                        | 是否允许进入下一阶段     |
| -------------------- | --------------------------- | -------------- |
| DRAFT                | 方案、设计、代码或规范草案已形成            | 不允许直接作为已验证成果   |
| NOT_RUN              | 尚未实际执行，或无法取得运行证据            | 不允许            |
| EXECUTED             | 已实际执行，并留存真实输出               | 进入复核，不代表通过     |
| PENDING_VERIFICATION | 已有执行产物，等待独立检查               | 等待验收           |
| PASSED               | 所有必需验收项通过，无阻断缺陷             | 允许进入交付         |
| CONDITIONAL_PASS     | 无阻断缺陷，剩余事项有负责人、期限、影响范围及补救方案 | 经明确批准后允许限定范围交付 |
| FAILED               | 存在阻断缺陷、关键证据缺失或验收失败          | 不允许交付          |
| DELIVERED            | 已按批准范围交付，并核对交付物             | 本周期交付完成        |
| ARCHIVED             | 版本、底稿、证据、变更记录和追溯索引已归档       | 当前版本收口         |

特别规则：

1. DRAFT 是方案状态，不是运行结果。
2. NOT_RUN 必须明确写出尚未执行的项目。
3. EXECUTED 只证明执行发生，不证明执行正确。
4. PASSED 必须有验收证据。
5. CONDITIONAL_PASS 不得掩盖安全、数据完整性或权限阻断项。
6. FAILED 必须保留失败证据，不能通过删除失败记录来制造通过结果。
7. DELIVERED 和 ARCHIVED 是两个不同状态：交付完成不等于归档完成。

# 1. 第一阶段：最小闭环 Micro Loop / PoC

## 1.1 阶段定位

目标：用最小样本证明一个核心机制可以实际运行。

准入条件：

- 已明确要验证的具体问题。
- 至少有一份可用原始样本。
- 已明确预期输入和输出。
- 已定义成功与失败的判断标准。
- 已确定测试环境及权限范围。
- 不会直接触碰生产数据或破坏原始资料。

禁止准入：

- 目标不清楚。
- 没有可复现的样本。
- 不知道测试会修改哪些数据。
- 需要未经授权的外部访问。
- 测试可能影响生产系统而没有隔离环境。

## 1.2 标准输入

```
project_id: CNSH-项目编号
module_id: MODULE-编号
task_id: TASK-编号

objective: 核心验证目标
hypothesis: 核心假设

source:
  original_id: 原始样本编号
  source_type: text | formula | image | table | code | data
  source_location: 原始位置
  source_version: 原始版本
  content_hash: SHA-256值或UNKNOWN

environment:
  os: UNKNOWN
  runtime: UNKNOWN
  dependencies: UNKNOWN
  network_required: false

test:
  input_sample: 最小测试输入
  expected_output: 预期输出
  pass_criteria: 成功标准
  fail_criteria: 失败标准

permission:
  mode: READ_ONLY | CANDIDATE_WRITE
  production_access: false
```

## 1.3 标准操作步骤

**步骤 1：固定原始样本**

- 保留原始文件或原始输入。
- 记录来源、版本、日期和内容类型。
- 对可读取的文件计算 SHA-256。
- 不允许为了方便而修改原始样本。
- 如果来源或哈希无法确认，标记 UNKNOWN。

检查点：

- 原始样本是否可再次读取？
- 样本是否与测试对象一致？
- 是否能确定测试使用的是哪个版本？

**步骤 2：建立隔离测试对象**

- 从原始样本复制测试副本。
- 明确测试副本路径。
- 测试只操作副本。
- 记录依赖版本和运行环境。
- 不安装或修改全局依赖，除非获得单独授权。

检查点：

- 测试是否与原始文件隔离？
- 是否存在生产数据写入路径？
- 是否存在自动联网、上传或后台执行行为？

**步骤 3：执行最小功能**

只验证一个核心机制，例如：

- 一条公式能否正确解析。
- 一张表能否建立并读取。
- 一份 JSON 能否通过结构校验。
- 一张 SVG 能否正常显示。
- 一个 3D 场景能否创建并旋转。
- 一段动画能否按时间变化。
- 一条 Notion 转换路径能否保留规定字段。

不在 PoC 阶段同时加入所有功能。

**步骤 4：记录真实输出**

至少保存：

- 输入样本。
- 执行命令或操作步骤。
- 运行环境。
- 实际输出。
- 错误信息。
- 执行时间。
- 测试结果。
- 相关日志或截图。

**步骤 5：对照预期结果**

将实际输出与预期输出逐项比较。

结果只能填写：

- MATCH：符合预期。
- PARTIAL_MATCH：部分符合。
- MISMATCH：不符合。
- UNKNOWN：证据不足。

## 1.4 第一阶段输出物

```
01_MICRO_LOOP/
├── source/
│   └── original_sample
├── candidate/
│   └── prototype
├── tests/
│   └── test_cases
├── evidence/
│   ├── execution_log
│   └── actual_output
└── report/
    └── micro_loop_report.md
```

## 1.5 第一阶段出口

只有取得真实运行证据，才可将方案从 DRAFT / NOT_RUN 更新为 EXECUTED。

如果实际输出满足核心验收条件，可以进入 PENDING_VERIFICATION。

如果没有运行，只能保留 DRAFT 或 NOT_RUN。

# 2. 第二阶段：结构与底座串联 Integration & Base Alignment

## 2.1 阶段定位

目标：将已验证的小闭环接入统一系统，避免每个模块使用自己的字段、格式、权限和路由。

准入条件：

- 第一阶段已有真实运行产物。
- 原始输入和实际输出可追溯。
- 核心功能已通过初步检查。
- 已确定统一数据字段。
- 已明确接入系统的权限边界。

## 2.2 统一元数据规范

每个对象必须尽可能具有以下字段：

```
{
  "object_id": "唯一对象编号",
  "object_type": "formula|document|image|scene|dataset|code",
  "title": "对象标题",
  "source": {
    "source_id": "来源编号",
    "source_type": "local|notion|user_input|external",
    "source_location": "来源位置",
    "source_version": "来源版本"
  },
  "content": {
    "original_format": "原始格式",
    "structured_format": "结构化格式",
    "content_hash": "SHA-256或UNKNOWN"
  },
  "version": {
    "revision": 1,
    "parent_revision": null,
    "change_type": "INITIAL"
  },
  "permissions": {
    "read": true,
    "write": false,
    "execute": false,
    "sync": false
  },
  "relations": [],
  "render": {
    "renderer": "UNKNOWN",
    "render_version": "UNKNOWN",
    "render_profile": "DEFAULT"
  },
  "verification": {
    "status": "NOT_RUN",
    "evidence": []
  }
}
```

说明：

- 作者身份必须有独立可信来源，不能从哈希推断。
- 权限字段是待执行的策略描述，不代表系统已经实施权限控制。
- `null`、`UNKNOWN`、空数组和空字符串含义不同，不能随意混用。
- 真实项目可根据内容类型扩展字段，但不得静默改变既有字段含义。

## 2.3 标准操作步骤

**步骤 1：字段对齐**

- 将 PoC 输入、输出映射到统一字段。
- 保留原始字段名和映射关系。
- 不认识的字段进入 `extensions` 或隔离区。
- 不允许直接丢弃无法映射的字段。

检查点：

- 原始信息是否仍然完整？
- 是否存在字段类型冲突？
- 是否出现同名字段但语义不同？

**步骤 2：建立原始留存与结构化暂存**

- 原始文件独立保存。
- 结构化数据保存为独立版本。
- 两者通过 object_id 和 revision 关联。
- 转换过程保存工具、版本、参数和日志。
- 转换失败不得覆盖原始数据。

**步骤 3：建立关系与索引**

- 建立对象之间的来源、派生、引用、依赖和关联关系。
- 区分单向关系与双向关系。
- 关系必须有类型和来源。
- 删除或失效关系时保留审计记录。
- 检索索引可重建，不应成为唯一原始数据来源。

**步骤 4：配置存储与渲染路由**

根据对象类型选择：

- 原始文件仓库。
- SQLite 元数据与关系库。
- 全文检索索引。
- 2D 渲染器。
- 3D 渲染器。
- 动态渲染器。
- Notion 或其他展示适配器。

路由规则必须记录：

- 输入类型。
- 目标格式。
- 目标引擎。
- 适配器版本。
- 转换参数。
- 失败回退路径。

**步骤 5：建立往返检查**

尝试：\
原始输入 → 结构化表示 → 目标格式 → 再次读取。

对比：

- 内容是否丢失？
- 公式是否变化？
- 关系是否断裂？
- 元数据是否保留？
- 表现差异是否可解释？

## 2.4 第二阶段输出物

```
02_INTEGRATION/
├── schemas/
│   └── object.schema.json
├── mappings/
│   └── field_mapping.json
├── storage/
│   └── storage_policy.yaml
├── relations/
│   └── relation_model.json
├── routing/
│   └── renderer_routes.yaml
├── adapters/
│   └── adapter_registry.json
└── report/
    └── integration_report.md
```

## 2.5 第二阶段出口

必须证明：

- 原始内容没有被覆盖。
- 结构化内容可识别。
- 元数据可读取。
- 关系可查询。
- 渲染路径可追踪。
- 转换失败可以回退。

状态：PENDING_VERIFICATION。

# 3. 第三阶段：验收与复核 Verification & Acceptance Gate

## 3.1 阶段定位

目标：独立判断交付对象是否符合原始要求，而不是由开发者自行宣布成功。

准入条件：

- 第二阶段产物已形成。
- 测试环境和版本已固定。
- 原始输入可追溯。
- 验收清单已明确。
- 测试范围和权限已批准。

## 3.2 验收项目

| 验收维度 | 检查内容      | 通过标准         |
| ---- | --------- | ------------ |
| 完整性  | 输入、输出、元数据 | 关键字段无意外缺失    |
| 正确性  | 公式、计算、结构  | 与独立预期结果一致    |
| 一致性  | 不同格式之间转换  | 差异已解释且符合规范   |
| 可追溯性 | 来源、版本、变更  | 能找到原始输入和派生关系 |
| 安全性  | 权限、网络、执行  | 无未经授权的访问和执行  |
| 可恢复性 | 备份、回滚     | 能恢复到已记录版本    |
| 兼容性  | 目标环境和格式   | 目标环境达到规定支持范围 |
| 性能   | 加载、渲染、查询  | 达到预先设定的阈值    |
| 可访问性 | 字体、缩放、交互  | 满足约定的使用要求    |

## 3.3 缺陷分级

**BLOCKER｜阻断**

例如：

- 原始内容丢失。
- 计算结果错误且影响核心功能。
- 未授权写入或数据外传。
- 版本关系断裂。
- 权限绕过。
- 无法恢复关键数据。

处理：必须修复并重新验收，不允许放行。

**MAJOR｜重大缺陷**

例如：

- 关键格式转换不一致。
- 主要交互不可用。
- 核心渲染路径失败。
- 关键字段无法追溯。

处理：原则上修复后复测；是否允许限定范围放行必须有书面批准。

**MINOR｜常规缺陷**

例如：

- 非核心样式偏差。
- 不影响内容正确性的显示问题。
- 非关键性能优化项。

处理：记录责任人和修复计划。

**DEVIATION｜设计偏差**

实际结果与原始设计不同，但可能合理。

处理：说明差异、影响和批准依据，不得擅自把偏差改写成原始要求。

**DEFERRED｜遗留项**

当前周期暂不处理的事项。

处理：明确影响范围、负责人、目标版本和复核日期。

## 3.4 标准验收步骤

1. 对照原始需求逐项检查。
2. 对照原始样本和实际输出。
3. 复算关键公式或执行独立测试。
4. 检查边界条件、异常输入和失败路径。
5. 检查不同渲染器的内容一致性。
6. 检查权限、网络访问和数据写入范围。
7. 检查备份与恢复。
8. 检查来源、版本、哈希和变更记录。
9. 汇总缺陷与遗留项。
10. 签发验收结论。

## 3.5 放行规则

PASSED：

- 所有强制验收项通过。
- 阻断缺陷为零。
- 证据完整。
- 无未批准的权限扩大。

CONDITIONAL_PASS：

- 阻断缺陷为零。
- 剩余事项不影响批准的交付范围。
- 每项遗留问题有负责人、期限、影响和补救措施。
- 已明确限制条件并获得授权。

FAILED：

- 存在阻断缺陷。
- 关键证据缺失。
- 结果无法复现。
- 原始数据或权限边界受到破坏。

## 3.6 第三阶段输出物

```
03_ACCEPTANCE/
├── acceptance_checklist.md
├── test_results.json
├── defect_register.csv
├── regression_report.md
├── security_report.md
├── recovery_report.md
└── acceptance_decision.md
```

# 4. 第四阶段：正式交付与归档 Delivery & Handover

## 4.1 阶段定位

目标：把已经放行的成果交给目标使用者或目标系统，并留下完整账本。

准入条件：

- 状态为 PASSED，或经批准的 CONDITIONAL_PASS。
- 交付范围明确。
- 交付物清单完整。
- 访问权限已确认。
- 变更记录和验收证据可用。
- 已制定交付失败的回退方案。

## 4.2 标准操作步骤

**步骤 1：生成交付包**

包括：

- 正式文件。
- 结构化数据。
- 必需依赖或依赖清单。
- 配置文件。
- 使用说明。
- 验收报告。
- 版本与变更记录。
- 遗留问题清单。

**步骤 2：同步目标载体**

目标载体可以是：

- 本地文件仓库。
- SQLite 数据库。
- Notion 页面。
- 文档库。
- 其他经批准的系统。

同步时必须：

- 记录目标位置。
- 记录同步方式。
- 核对目标对象数量。
- 核对文件大小和哈希。
- 核对权限状态。
- 记录失败项。

**步骤 3：冻结交付版本**

- 固定版本号。
- 固定配置和依赖版本。
- 生成交付清单。
- 保存内容哈希。
- 记录交付时间。
- 不允许静默修改已冻结版本。

后续修改必须创建新版本，并保留父版本关系。

**步骤 4：归档追溯账本**

至少记录：

- 原始来源。
- 设计版本。
- 代码或配置版本。
- 执行证据。
- 验收结论。
- 交付目标。
- 交付结果。
- 遗留事项。
- 回滚位置。

## 4.3 第四阶段输出物

```
04_DELIVERY/
├── release/
├── manifests/
│   └── delivery_manifest.json
├── verification/
│   └── final_acceptance_report.md
├── changelog/
│   └── changelog.md
├── rollback/
│   └── rollback_plan.md
└── archive/
    └── traceability_index.json
```

## 4.4 最终出口

DELIVERED：目标位置已确认，交付清单核对完成。

ARCHIVED：原始底稿、交付版本、验收证据和追溯索引已归档。

# 5. 各类底座的专项 SOP

以下模块全部执行上述四阶段流程，不允许跳过统一验收。

## 5.1 原始内容留存与结构化暂存

**PoC**

- 选取一份文本、一份公式或一份结构化样本。
- 测试读取、原样保存、结构化提取。
- 对比原始内容与输出内容。

**Integration**

- 建立 original、structured、derived 三类对象。
- 每次转换记录工具、版本、参数和来源。
- 原始文件只读保存。
- 派生内容通过 parent_revision 关联原始版本。

**Acceptance**

- 中文、英文、数学符号、特殊字符和换行不丢失。
- 元数据字段可读取。
- 失败转换不覆盖原始文件。
- 可根据来源编号找到原始样本。

**Delivery**

- 输出原始文件、结构化文件、转换报告和版本索引。

## 5.2 本地存储、SQLite、索引与关系库

**PoC**

- 创建一张测试表。
- 插入一条记录。
- 查询并读取。
- 关闭后重新打开数据库，再次读取。

**Integration**

- 区分稳定对象表、不可变修订表、关系表、标签表和检索索引。
- 版本记录只追加。
- 索引可以重建。
- 原始文件独立于数据库保存。
- 明确备份策略和路径权限。

**Acceptance**

- 重复写入有明确行为。
- 版本不能静默覆盖。
- 关系查询正确。
- 数据库重启后内容一致。
- 备份恢复通过。
- 中文全文检索经过真实样本测试。
- FTS 索引与原始数据一致。

**Delivery**

- 数据库文件、Schema、迁移记录、备份、恢复报告和数据字典一起交付。

## 5.3 2D 图形渲染

**PoC**

- 选取一个简单图形。
- 测试 SVG 或 Canvas 输出。
- 检查缩放、文字、线条和布局。

**Integration**

- 图形对象与业务数据分离。
- 记录坐标系、节点、边、样式和渲染器版本。
- 同一份结构数据可以交给不同 2D 渲染器。

**Acceptance**

- 节点与连接关系准确。
- 缩放后文字和线条可读。
- 导出与屏幕显示内容一致。
- 不支持的元素有明确降级方案。

**Delivery**

- 结构数据、渲染配置、预览图、导出文件和测试报告一起交付。

## 5.4 3D 场景与模型渲染

**PoC**

- 创建一个三维场景。
- 放置一个几何体。

**Integration**

**Acceptance**

- 坐标与单位正确。
- 模型关系和层级正确。
- 相机控制正常。
- 材质和光照表现可复现。
- 大模型加载有性能限制。
- 低能力设备有降级路径。
- 不因渲染失败修改原始模型。

**Delivery**

- 场景数据、模型资源、材质配置、相机配置、依赖清单和兼容性报告一起交付。

## 5.5 动态与实时渲染

**PoC**

- 创建一个可变化的属性。

**Integration**

**Acceptance**

**Delivery**

- 动画配置、时间轴数据、运行记录、性能报告和降级说明一起交付。

**Delivery**

# 7. 通用回退与异常处理 SOP

遇到以下情况，立即停止当前阶段的自动推进：

| 异常          | 处理动作             | 回退位置       |
| ----------- | ---------------- | ---------- |
| 输入文件损坏      | 保留错误日志，检查备份和原始来源 | P1 输入固定    |
| 结构字段冲突      | 隔离未知字段，不强行覆盖     | P2 字段映射    |
| 数据库写入失败     | 停止写入，检查事务和备份     | P2 存储测试    |
| 渲染错误        | 保留结构数据，切换测试渲染器   | P1/P2 渲染验证 |
| 3D 性能不足     | 降低场景复杂度或采用降级路径   | P2 引擎适配    |
| 动画状态错误      | 固定时间输入，复现状态变化    | P1 动态 PoC  |
| Notion 转换丢失 | 停止覆盖，保存源与目标差异    | P2 平台适配    |
| 权限异常        | 立即停止相关操作         | 安全准入复核     |
| 验收失败        | 保留失败证据，建立缺陷单     | 对应开发阶段     |
| 交付校验失败      | 不冻结、不宣布交付完成      | P3 验收      |

回退原则：

1. 先停止。
2. 再保存现场。
3. 记录错误和影响范围。
4. 确认原始数据完整。
5. 回到最近一个已验证版本。
6. 修复后重新执行受影响的测试。
7. 追加新的变更记录，不覆盖旧记录。

# 8. AI 派活总指令

你是 CNSH 工程执行与审计助手。

请严格遵守本 SOP，按照四阶段流程推进任务：

1. Micro Loop：最小样本验证。
2. Integration：结构、元数据、存储和路由串联。
3. Acceptance：独立验收与缺陷定级。
4. Delivery：正式交付与追溯归档。

执行要求：

- 先读取现有资料和工程结构，不要假设系统已经具备某项能力。
- 先报告 FOUND / MISSING / UNKNOWN / NOT_RUN。
- 明确本次任务的范围、输入、输出、权限和回退点。
- 优先使用只读检查。
- 写入操作必须限定到候选副本或明确授权的目标。
- 原始数据不覆盖，正式版本不静默修改。
- 每一步都记录实际执行结果。
- 不得将 DRAFT 写成 EXECUTED。
- 不得将 EXECUTED 写成 PASSED。
- 不得把局部测试通过写成全系统通过。
- 所有未运行的测试必须标记 NOT_RUN。
- 所有缺陷和遗留事项必须保留。
- 遇到阻断问题立即停止，不得绕过验收门。
- 需要外部同步、网络访问、安装依赖或生产写入时，先检查权限和授权范围。
- 交付时提供文件清单、版本、哈希、验收证据、遗留项和回退方法。

A. 任务范围\
B. 当前资产与证据\

I. 交付清单\
J. 最终结论

如果任务过大，先拆分为可独立验证的模块，但必须保持统一元数据、权限、版本和审计规则。

**最终原则：先证明能运行，再证明能协作；先证明正确，再正式交付。**
